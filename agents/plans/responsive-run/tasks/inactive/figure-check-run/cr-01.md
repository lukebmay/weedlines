## What held

The change fits the task and the runtime part. `src/weedlib/figures.py`, the surround module, and the solvers were not edited. `build_surrounds` and `generate_weeds` still run in this process. The guide was not edited.

`_geometry_worker` is a module-level spawn target. `_spawn_ask` uses `multiprocessing` spawn, not fork, and not a thread. The child sends plain messages and shows no window. It does not return a `QPainterPath`. A `segment` message is appended to the existing segment queue. This ask does not send one.

`_shown` starts one classify ask and returns. The subject ask starts only after that result is stored on the GUI thread. Swap starts a subject ask. A plugin color calls `refresh_preview` on the stored paths and does not classify again. `_ask_surrounds` runs only after those regions are stored, and only when a surround is already started.

The GUI thread rebuilds `QPainterPath` and `ArrowPath` from element kinds and coordinates. Fill rules travel as `odd` or `wind`. Kinds use `_plain_int`. A cubic, a quad, a winding rule, and the boolean subject and weed area round-trip to the same elements. The painted arrows match the library arrows. The written correction arrows match those same paths. A parent patch of `classify_figures` and `build_arrow_paths` stays empty. `dialog.worker_calls` is the count.

`ready` runs after `refresh_preview`, with the window visible. Until that paint, Start, Swap, and the surround controls stay inactive. Close still works. Pause and Cancel are mirrored onto the child and take effect at the progress checks. The checks in `figures.py` were not removed. Close sets the drop flag and the cancel event. It does not join the geometry process and does not kill it. A result that arrives after Close is not applied. A focus name is stored on `dialog.focus_mark` and is not painted. Child stdout and stderr reach the algorithm log through `append_log`.

`_ASK_HOLD`, when set, is a tight loop in the child before the library call. Unset, it does nothing. The same loop on a thread in this process blocks a GUI timer. The same hold in the child lets a 0ms timer fire before `ready`, while the dialog is visible and `_shown` has returned.

`_on_swap` waits in `processEvents` until the subject ask finishes, so the click returns after the new paint. The library call for that ask is still in the child. That loop is not the figure check running on the GUI thread.

`on_close` still calls `thread.join(2.0)` when `state['busy']` and the solver thread is alive. A geometry ask sets `busy`, but that solver thread is not alive during the ask, so this close does not wait and does not join the geometry process. The join is not worse than on the parent.
