## What held

The change fits the task and the runtime part.
`src/weedlib/surround.py` was not edited. The guide was not
edited. Frame, grid, and island-hop still start `generate_weeds`
on the existing thread. This step does not call it and does not
write a result.

`_ask_surround` is a branch of `_geometry_worker`, started with
`multiprocessing` spawn through `_spawn_ask`. There is no second
target. The child sends `surround` messages of element kinds and
coordinates, plus `odd` or `wind`. It does not send a
`QPainterPath`. The GUI thread rebuilds the paths in
`_after_surround`, and `refresh_preview` paints those. A parent
patch of `build_surrounds` stays empty. `dialog.worker_calls`,
`dialog.surround_args`, and the painted strokes are the proof.

Start, a distance or join change, a swap after the new regions
are stored, and returning to this mode each start one surround
ask. One ask at a time. The parent waits with `QTimer.singleShot`.
It does not join or kill the child. If the distance, join gap, or
swap changed while that ask was in flight, the arrival does not
paint those paths and the newer ask starts. A swap starts the
subject ask first, then the surround.

Clear All is still `on_cancel`. It sets the cancel event and does
not kill the child. If abort is set when the paths arrive, they
are discarded and the step returns to the wait. Pause is mirrored
and blocks at the progress checks. Those checks in `surround.py`
were not removed. A focus name is stored on `dialog.focus_mark`
and is not painted. Child stdout and stderr reach the algorithm
log through `append_log`.

`_ASK_HOLD`, when set, is the same tight loop in the child before
the library call. A hold in the child lets a 0ms timer fire before
the surround is painted. The dialog stays visible. Start does not
run the solver or enable Apply. The same loop on a thread in this
process still blocks a GUI timer.

Opening stays locked until the first paint is stored. The opening
flag drops before `set_controls`, so distance, join, swap, and
mode unlock. During a surround ask those four stay live.
`_reap_proc` still calls `join(0)` only after the process is
already dead. That reaps it. It does not wait, and it does not
kill.

`on_close` still joins the solver thread only when that thread is
alive. A surround ask sets `busy` and does not start that thread,
so this close does not wait on the geometry process. The join is
not worse than on the parent.
